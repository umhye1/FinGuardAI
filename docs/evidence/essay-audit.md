# 자소서 구현 대조 (2026-09-11)

코드 존재, 실제 실행 결과, 과거 경험 서술을 구분해 점검했다. 이 문서는 개발 에이전트의 검토이며 금융 전문가의 인증이 아니다.

| 자소서 주장 | 확인 결과와 정확한 범위 |
| --- | --- |
| RAG 검색·생성 파이프라인 | `rag.py`, `repository.py`, `provider.py`에 구현. OpenAI와 Gemini 선택 가능. |
| 백엔드 검증 | `ChatAnswerWriter`가 문서 처리 상태, 인용 청크, 내용 해시, metadata 스냅샷, 검토기한을 대조. |
| 근거 충돌 시 보류 | 검토자가 정규화한 `claims`의 동일 주제·항목 값이 다르면 생성 전에 보류. 임의 문서 전체의 자연어 모순 탐지기는 아님. |
| 추가 질문 | 질문에서 지원하는 피해 유형을 특정하지 못할 때 추가 질문. 모든 충돌을 추가 질문으로 해결하는 기능은 아님. |
| 사례·공식 지침 분리 | `CASE`와 `OFFICIAL_GUIDANCE`를 구분하고 사례는 대응 지침 인용에서 제외. |
| 기관·게시일·적용대상·버전 | metadata에 존재. 적용대상은 현재 `KR_CONSUMER` 한 종류만 지원. |
| 공식·최신 우선 | 등록된 검토 corpus에서 같은 발행기관·문서계열·적용대상의 최신판 선택. 기관이 다르면 날짜만으로 덮어쓰지 않음. |
| 키워드+벡터 결합 | 한국어 부분문자열 키워드 순위와 모델별 코사인 검색 순위를 RRF로 결합. 임베딩 미등록 시 키워드 경로 사용. |
| 질문별 필수 문서 | 개별 질문마다 지정하는 관리 UI가 아니라 송금·스미싱·소액결제 유형별 필수 문서계열 규칙. |
| 실제 자료 검증 | 공식 페이지 3개 기반 요약 5건과 오프라인 평가 존재. 실제 모델 답변 평가는 API 키 설정이 완료되어야 실행 가능. |
| 실제 기관·시점별 충돌 발견 | 현재 corpus에서 실제 충돌이 발생했다는 재현 기록 없음. 충돌 검증은 명시적인 합성 fixture로 수행. |
| 처음 실패하고 이후 개선했다는 경험 | 기능 추가 커밋으로 과거 경험의 사실 여부를 입증할 수 없음. 실제 작업 기록에 맞게 서술해야 함. |

## 원문과 요약 대조

다음 공식 원문을 다시 열어 저장된 요약의 핵심 안내와 적용범위를 대조했다.

- [관계기관 합동 안내, 2025-01-20](https://www.fsc.go.kr/no010101/83889): 계좌 송금 피해 안내 및 카드 배송 사칭 사례의 출처. 금융감독원이 참여했으나 게시 사이트는 금융위원회다.
- [KISA 안내, 2025-04-01](https://spam.kisa.or.kr/spam/na/ntt/selectNttInfo.do?bbsId=1001&mi=1019&nttSn=2642): 문자 확인·신고, 악성앱 대응, 소액결제 관련 서류 처리의 출처. 요약은 원문의 모든 조치·예외를 포함하지 않는다.
- [통합신고센터 안내, 2023-09-26](https://www.fsc.go.kr/po010101/80830): 과거 기관별 신고창구 설명과 통합 이후 안내를 구분했다. 옛 창구 설명을 현행 절차로 합치면 안 된다는 설계 근거는 되지만, 모델이 실제로 그런 오답을 냈다는 증거는 아니다.

## 확인된 구현에 맞춘 자소서 초안

**[근거가 충돌하면 멈추는 AI]**

금융사기 대응 AI를 개인 프로젝트로 개발하며 RAG 검색·생성 파이프라인과 백엔드 검증 로직을 구현했습니다. 공식 자료를 검토하면서 같은 문서에도 과거 제도 설명과 현재 대응 절차가 함께 등장하고, 피해 유형에 따라 필요한 안내가 달라진다는 점에 주목했습니다. 의미가 비슷한 문서를 검색하는 것만으로는 답변에 사용해도 되는 근거를 구분하기 어렵다고 판단했습니다.

이에 사례와 공식 대응 지침을 분리하고, 발행기관·게시일·적용대상·버전을 메타데이터로 관리했습니다. 동일 기관·문서계열에서는 최신 자료를 선택하고, 키워드 검색과 벡터 검색을 결합했습니다. 송금·스미싱·소액결제 유형별 필수 문서계열을 정하고, 검토해 구조화한 대응 절차가 충돌하거나 필수 근거가 부족하면 답변을 보류하도록 구현했습니다. 피해 유형이 불분명하면 추가 질문으로 전환하고, 백엔드에서는 인용 문서의 처리 상태와 내용·메타데이터가 생성 시점의 근거와 일치하는지 검증했습니다.

공식 출처 기반 요약 자료를 등록하고, 충돌·자료 누락·버전 변경을 재현하는 테스트로 정책의 동작을 확인했습니다. 이 과정에서 금융 AI의 품질에는 모델 성능뿐 아니라 모델이 맡을 판단과 시스템이 검증할 영역을 구분하는 설계가 중요하다는 점을 배웠습니다. KB에서도 금융업무의 특성과 판단 근거를 고려해 AI의 역할을 정하고, 근거가 부족한 상황을 시스템이 통제할 수 있도록 설계하겠습니다.

이 초안은 본인이 구현·검증 내용을 이해하고 설명할 수 있는 범위에서 사용해야 한다. 실제 생성 평가를 완료하기 전에는 실제 답변 정확도를 검증했다거나 검색 정확도를 높였다는 문장을 추가하지 않는다.
